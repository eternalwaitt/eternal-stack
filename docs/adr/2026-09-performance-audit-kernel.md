# Performance audit kernel and conditional domain references

Status: accepted for implementation; 2026-09-08. This is an unreleased capability change. `VERSION` remains the shipped 0.11.1; follow the normal release process before changing it or tagging.

## Diagnosis and decision

The former six-lane registry had only six result checks. Most accepted a nonempty evidence string, so one row could conceal missing subchecks and a clean statement did not prove instrumented investigation. Worklist examples favored Next.js and Prisma. Source hashes were asserted labels rather than fine receipt evidence files. The baseline already separated field/lab evidence and treated undersampled runtime trends as inconclusive; recent provider incident work correctly prohibited false closure and distinguished build/runtime memory. Preserve those mechanisms.

Choose a mandatory deterministic kernel plus four conditional, repo-owned references. Keep six scheduling lanes for compatibility, but require independent subcheck receipts for database, runtime, cache, requests, React, browser, bundle, delivery, load, background, build and platform. The registry exports those checks, the artifact validator requires them, and missing optional skills cannot alter the set. No new separately installed sub-skills are needed: focused references share one receipt protocol and arrive with the parent skill, avoiding extra trigger and synchronization surfaces.

| Architecture | Benefit | Cost / decision |
| --- | --- | --- |
| Comprehensive single skill | Easy single trigger | Large always-loaded context; instructions alone cannot enforce depth. Rejected. |
| Orchestrator plus separately installed domain skills | Independent expertise and reuse | More install/trigger/version failure paths; no existing need for independent entrypoints. Deferred. |
| Mandatory kernel plus conditional references | Enforced common evidence, low startup context, portable sequential execution | Requires classification and receipt authoring. Chosen. |
| External skills as primary implementation | Strong framework/provider detail | Scope caps, unavailable tools, version drift and incompatible completion rules. Supplemental only. |
| Signal-only candidate engine | Efficient prioritization, especially provider telemetry | Blind to uninstrumented paths and no-traffic surfaces; use signals to order investigation, not exclude coverage. |

## Before / after and limits

Before: six broad report results, textual clean evidence, source-skewed discovery examples, good baseline and memory-incident rules. After: fine registered checks, conservative stack-neutral inventory, explicit source/runtime reconciliation, per-check receipts with actual evidence-file hashes, strict clean/partial separation, optional contributor fallback, experiment decisions and source/distribution parity. Core Web Vitals remain one browser subcheck, not the full audit.

This is a contract and investigation workflow, not a universal profiler or semantic route compiler. Agents must classify framework/runtime surfaces; scripts cannot attest that a supplied trace is truthful or that external registrations were all found. Three repeats are not sufficient for every statistical claim. External skills are not installed or behavior-certified. Missing runtime credentials, representative data, browser/profiler access, provider telemetry or authorized load target remain named dependencies. Behavioral prompts and deterministic adversarial tests exercise contract failures; live agent recall requires an explicitly recorded evaluation run.

Installation is separate. The source helper can compare installed/cached/staged roots read-only. A stale installed copy is not repaired by a source test pass. No commit, publish, deploy or global install is part of this change.

### Performance expertise and investigation depth

The performance contract v2 reuses the bundled `orpc-patterns` (entrypoint `orpc-fullstack`), `prisma-expert` and `sql-optimization-patterns` resources when detected, plus React/Next and conditional query-cache, runtime, queue, streaming and provider playbooks. Resource hashes and version review fence inherited examples. Every check/surface cell requires an initial investigation and full challenge sweeps until a sweep adds no findings. Findings are uncapped; prior-run reconciliation exposes missed issues and audit-quality failures. See [the routing and depth contract](../../skills/etrnl-audit-performance/references/conditional-performance.md).

Primary-document cross-check for the specialist integration: [Prisma v6 relation strategies](https://www.prisma.io/docs/orm/v6/prisma-client/queries/relation-queries), [Prisma driver-owned pooling](https://docs.prisma.io/docs/orm/v6/reference/prisma-client-reference), and [TanStack Query retries](https://tanstack.com/query/latest/docs/framework/react/guides/query-retries). These support version-aware checks for query strategy, driver pool ownership and layered retry amplification; they do not establish the versions used by a future target. Existing bundled source licenses and attribution are unchanged.
