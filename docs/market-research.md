# Market research: coding companions, agent workflows, and tools

**Research date: 2026-10-10.** This report informs Eternal Stack’s design for people working inside Claude Code and Codex, from personal tasks to large enterprise repositories. It compares documented mechanisms and selected pinned source snapshots. It is not a product ranking, market-share study, certification, or benchmark of task quality, cost, speed, or safety. Links to mutable vendor documentation describe the material reviewed on the research date; pinned source links identify the exact revision reviewed.

## How to read this comparison

The landscape includes different layers. Claude Code, Codex, OpenCode, Pi, Cline, Cursor, Copilot, Aider, and Continue are coding hosts or agents. Superpowers, GSD Core, gstack, ECC, Compound Engineering, BMAD, Spec Kit, OpenSpec, and AIOX provide workflow or capability packages for coding hosts. Oh My OpenAgent and Ruflo extend particular runtimes. LangGraph, AutoGen, and CrewAI are libraries for building agent applications. Gas Town coordinates ongoing work across projects and workers. These systems solve related problems, but they are not interchangeable install choices.

Evidence is graded by what was examined:

- **Pinned source** means a repository revision and relevant source/docs were inspected. It does not mean that the project was installed or its task quality empirically verified.
- **Current documentation** means first-party documentation or the project’s own repository was checked on the research date. It can change and does not independently validate behavior.
- **Adjacent pattern** means a useful runtime or tool mechanism, not a direct replacement for a companion inside Claude Code and Codex.
- No candidate was installed, exercised end-to-end, costed, penetration-tested, or compared under controlled tasks. Product claims, community popularity, and benchmark reports are not evidence of superiority for Eternal’s intended work.

## Mechanisms with the clearest design value

### 1. Route by task size and risk, not by one universal process

GSD Core defines a direct inline `fast` path for trivial edits, a `quick` planner/executor path for bounded fixes/features, and a phase loop for larger work. Flags add discussion, research, or validation when needed. BMAD similarly says to skip process for a trivial edit, use a bounded `bmad-build` session for a small goal, and plan work that exceeds that session. Compound Engineering skips planning for one-step work or a known-cause bug and reserves multi-agent review for sensitive or large diffs. Those are concrete mechanisms for adapting process cost—not evidence that a particular threshold predicts success.

**Adopt:** a small direct lane, a structured change lane, and a durable program lane. Estimate independent dimensions: scope/dependencies, uncertainty, impact/reversibility, and need for independent work. High risk can require review even for a tiny diff; large scope can justify durable state even when risk is low. **Avoid:** requiring brainstorming, a plan file, multiple reviewers, or user selection of routine workflow steps on every request.

GSD source: [`handle-quick-and-fast-tasks.md` at pinned `651bd2f`](https://github.com/open-gsd/gsd-core/blob/651bd2f5ee100bb32118ab7e429bdfb1649b0f41/docs/how-to/handle-quick-and-fast-tasks.md), [phase-loop guidance](https://github.com/open-gsd/gsd-core/blob/651bd2f5ee100bb32118ab7e429bdfb1649b0f41/docs/explanation/the-phase-loop.md). BMAD: [build-a-change](https://github.com/bmad-code-org/BMAD-METHOD/blob/bda3c5929f672019b90f39a3ea27259d35d00974/docs/build/build-a-change.md), [planning-path selection](https://github.com/bmad-code-org/BMAD-METHOD/blob/bda3c5929f672019b90f39a3ea27259d35d00974/docs/plan/choose-a-planning-path.md). Compound: [work workflow](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/SKILL.md), [review escalation](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/docs/guides/ce-code-review.md).

### 2. Reviews need distinct purpose, bounded cycles, and freshness

Superpowers separates spec compliance from implementation quality after each delegated task, then performs a final whole-branch review. Its source caps repair rounds at five and the final review allows one fix dispatch/re-review. It also acknowledges the overhead: a new context per worker and reviewer, while its inline route costs one implementation context plus final review. This is an explicit loop bound, but not a whole-task cost limit: a plan with many tasks still scales worker and review calls.

gstack records review freshness against fingerprints of current source, marks absent or nonconverged evidence unverified/stale, and refuses to treat the same commit hash as proof. It also acknowledges that completion is reviewer-reported; freshness is provenance, not proof that the reviewer reasoned correctly. Compound Engineering routes quick/light reviews to the native reviewer, while deep mode selects personas by changed surface and deduplicates evidence-backed findings.

**Adopt:** reviews proportional to risk/diff, requirements-vs-quality separation for delegated work, evidence anchored to files/behavior, tree-bound freshness, and finite correction rounds. **Avoid:** treating reviewer logs as deterministic verification, or launching a committee where one targeted pass suffices. [Superpowers subagent workflow](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/SKILL.md), [gstack review](https://github.com/garrytan/gstack/blob/4e5bf1e454012c494648ea04c871b3c7b2e168ce/review/SKILL.md), [Compound review contract](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-code-review/SKILL.md).

### 3. Durable state is for multi-stage work; a transcript is not a ledger

Spec Kit’s workflow runner records a run ID, current step, and paused/failed/completed status; it can resume from persisted state and reports adapter failures separately from failures after execution began. It even documents that a failed state save can leave disk status at the last successful write. LangGraph distinguishes per-thread checkpointer state from cross-thread stores. CrewAI Flows can persist and resume or fork state. These are runtime mechanisms for longer operations, not reasons to create project artifacts for a typo.

**Adopt:** durable objective, acceptance conditions, decisions, state, evidence, remaining budget, and last checkpoint for large work; re-read current files and revalidate stale checks on resume. Keep direct work in host conversation. Design idempotency and failed-save behavior before claiming safe recovery. [Spec Kit workflows](https://github.com/github/spec-kit/blob/0443760542e7e5269724744a2ac55c4bd386d095/docs/reference/workflows.md), [LangGraph persistence](https://langchain-ai.github.io/langgraph/concepts/durable_execution/), [CrewAI flow persistence](https://github.com/crewAIInc/crewAI/blob/main/docs/v1.14.7/en/concepts/flows.mdx).

### 4. An aggregate budget must cover every participant and retry

Different projects bound different quantities. Superpowers caps local review-fix cycles; AutoGen supports `max_turns` but it can default to no limit; CrewAI agents have `max_iter` and optional execution time; Oh My OpenAgent supports per-agent `max_turns`; Ruflo federation supports hop and optional token/USD caps, while omitted caps can be infinite. None of these local controls automatically gives the coordinator one total task budget. Parallel work can shorten elapsed time while increasing token use and integration effort.

**Adopt:** one overall ceiling covering coordinator, workers, retries, reviews/fixes, elapsed time, and verification attempts. Reallocate inside the authorized total without asking the user to manage internal task distribution. Ask only for material scope, authority, or cost changes; an explicit user cap is never exceeded. On exhaustion, preserve state, report completed acceptance checks and remaining work, and stop without claiming success. [AutoGen turn limits](https://microsoft.github.io/autogen/stable/reference/python/autogen_agentchat.teams.html), [CrewAI agent limits](https://github.com/crewAIInc/crewAI/blob/main/docs/v1.10.1/en/concepts/agents.mdx), [Ruflo budget contract](https://github.com/ruvnet/ruflo/blob/main/v3/docs/adr/ADR-097-federation-budget-circuit-breaker.md).

### 5. Host parity is a tested adapter contract, not shared Markdown

AIOX documents Codex skill generation and validation but also notes lifecycle limits across IDEs. ECC documents native Codex and Claude installation while noting that Codex owns hook trust and does not share Claude’s installation scopes or hook profiles. Claude Code and Codex differ in project-instruction files, subagent semantics, permission boundaries, hooks, and session tools. MCP defines how tools/resources are exposed; it does not decide how a host manages model context or enforces permissions.

**Adopt:** one host-neutral workflow contract mapped to host-specific skill/agent/hook/tools, with each capability labeled `native-enforced`, `hook-enforced`, `advisory`, or `manual`. Test the same scenarios separately on each host. **Avoid:** parity claims based on copying prompt text or registering an MCP server. [AIOX Codex integration](https://github.com/SynkraAI/aiox-core/blob/4ef6530ff03b83aea953e4a426f95e012b8b70c5/README.en.md), [ECC support contract](https://github.com/affaan-m/ECC/blob/2d515e4fc2ddef97354769812cf3f7b9ec4e5124/README.md), [MCP architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).

### 6. Progressive loading avoids both a bare core and an all-context package

Agent Skills exposes names/descriptions before loading full capability instructions; Pi and host skill implementations use progressive disclosure. This permits broad availability while loading only applicable instructions. GSD’s source governs workflow/agent prompt sizes with a per-file baseline and tier caps, and warns that eagerly importing a “small” file does not reduce loaded context. OpenSpec’s default core path is small, while its expanded profile is explicitly selected. These mechanisms point to a middle architecture: install or make available a maintained library; activate a small number of distinct capabilities per task.

**Adopt:** compact catalog metadata, narrow triggers, lazy references, version/provenance, and host-specific availability checks. **Avoid:** exposing dozens of duplicate aliases, loading every skill body on every turn, or making the only options “instructions only” and “legacy full orchestration.” [Agent Skills specification](https://agentskills.io/specification), [GSD size-budget ADR](https://github.com/open-gsd/gsd-core/blob/651bd2f5ee100bb32118ab7e429bdfb1649b0f41/docs/adr/1610-workflow-agent-size-budget-ratchet.md), [OpenSpec profiles](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md).

### 7. Tool categories should map to outcomes and evidence

Tools should be optional adapters, not overlapping tool suites. Context7 retrieves version-relevant library documentation; Serena offers symbol/caller navigation; CodeGraph provides structural indexing; Repomix packages bounded repository context. Browser choices have distinct costs: Playwright MCP supports persistent exploration, CLI skills can produce smaller task-oriented output, agent-browser offers scoped snapshots/deltas, and Chrome DevTools can capture runtime/performance evidence. RTK filters command output, but must preserve exit status and diagnostic details. Beads provides persistent dependency-aware work tracking; Gas Town layers persistent workers, watchdogs, convoys and merge processing on top.

**Adopt:** choose one retrieval/browser/issue owner per task and report tool limitations. Use existing host/project tools where possible. **Avoid:** adding a daemon/index/browser tool because it appears in a competitor’s stack, or treating output/token savings as success without acceptance evidence. Sources: [Serena](https://github.com/oraios/serena), [Context7](https://github.com/upstash/context7), [CodeGraph](https://github.com/colbymchenry/codegraph), [Repomix](https://github.com/yamadashy/repomix), [RTK](https://github.com/rtk-ai/rtk), [Playwright MCP](https://github.com/microsoft/playwright-mcp), [agent-browser](https://github.com/vercel-labs/agent-browser), [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp), [Beads](https://github.com/gastownhall/beads), [Gas Town](https://github.com/gastownhall/gastown).

### Specialist skills, rules, and empirical evidence

Not every capability is an orchestrator. [Vercel Agent Skills](https://github.com/vercel-labs/agent-skills) is a focused React/Next skill set with composition patterns and task-specific guidance; its optimization workflow begins from metrics and investigates the surfaces those metrics implicate. Borrow its narrow scope and evidence-first optimization; do not apply framework rules outside their version/domain. [Impeccable](https://github.com/pbakaus/impeccable) packages focused design commands and deterministic detectors, separating product facts from visual direction. [Brooks lint](https://github.com/hyhmrright/brooks-lint) turns architecture lenses into traceable findings; its cited principles aid explanation but are not proof that a repository has a specific defect. These are optional specialist capabilities that should be routed by task, not loaded as universal instructions.

The broad policy lesson is to give each layer one job: project instructions state local invariants and commands; scoped technology rules govern applicable framework patterns; skills describe repeatable outcomes; agents provide independent context; deterministic tools enforce properties that should not depend on model obedience. Keep these sources differentiated so duplicate instructions do not compete. [Agent Skills](https://agentskills.io/specification) covers discoverability and capability structure, while [MCP architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture) standardizes tool/resource communication without defining host context or permission behavior.

Evidence about repository instruction files is mixed, and the studies measure different settings. [Evaluating AGENTS.md (v3)](https://arxiv.org/abs/2602.11988v3) reports no general success improvement and higher inference cost in its experiments; [On the Impact of AGENTS.md (v2)](https://arxiv.org/abs/2601.20404v2) reports efficiency benefits in its sample of repositories and pull requests. Neither evaluates Eternal’s task routing or companion experience. Likewise [SWE-bench](https://www.swebench.com/) measures issue-solving under benchmark environments, not onboarding, long-running recovery, host parity, or enterprise authority. Use these as evidence that evaluation setup matters, not as a universal vote for or against instructions.

## Shortlists by use case

These are **best-fit candidates to study for a mechanism**, not measured “best products.”

| Use case | Candidates to study | Why, and what not to infer |
|---|---|---|
| A beginner asking for everyday help in an existing repo | Native Claude Code/Codex; BMAD; OpenSpec core; Cline onboarding | Native hosts minimize runtime changes; BMAD/OpenSpec allow small entry paths. Their docs do not establish which is easiest in controlled use by Eternal’s users. |
| Tiny edit or known-cause bug | GSD `fast`/`quick`; BMAD direct/build; Compound quick route | Each has a mechanism to avoid heavyweight planning. Thresholds remain heuristics; test false escalation and missed complexity. |
| Large change with several independent tasks | GSD phase workflow; Superpowers subagent loop; Spec Kit workflows; AIOX stories | Dependency order, durable tasks and review are explicit. Their artifact/agent overhead may dominate a small change. |
| Review with limited false-positive noise | Compound tiered review; Superpowers spec/quality split; gstack freshness; ECC evidence/severity | Useful synthesis, freshness and bounded-loop patterns. Reviewer output is still a model claim; validate findings against source and tests. |
| Multi-day interrupted work | Spec Kit; GSD resume; LangGraph/CrewAI state model as runtime references; Codex native sessions | Durable checkpoints and status are appropriate. A workflow record cannot guarantee a failed side effect will not replay. |
| Multiple repositories and long-running parallel workers | Gas Town, Beads, Ruflo | Designed around persistence/coordination. Their operational load is justified only after measuring frequent concurrent work. |
| Library-specific troubleshooting or big-codebase navigation | Context7, Serena, existing CodeGraph index | Add task-specific docs/symbol retrieval. Freshness, dependency version and backend coverage need verification. |
| Browser/runtime verification | Existing browser host; one of Playwright CLI/MCP, agent-browser, Chrome DevTools | Select based on interaction versus trace needs and host availability. No need to layer several browser controllers. |
| Tool-visible policy and approvals | Gemini CLI, OpenCode, Goose | Source separates tool rules from confirmation; role/tool matrix is inspectable | Gemini’s workspace policy tier has a documented functionality caveat; Goose extensions may carry broad authority. |
| Specialist product comparison | Factory Droid; Amp; Kiro | Policy and managed configuration (Factory), code search/delegation (Amp), cross-surface steering/spec workflow (Kiro) | First-party documentation only; no implementation, live deployment or surface evaluation for these products. |
| Remote async coding and handoff | Cursor Background Agent; Copilot cloud agent; Kiro web/cloud harness; OpenHands Agent Canvas/Server | Separates local interaction from remote execution/PR delivery; Canvas selects Agent Server backends | Remote network, credentials, retention and review differ; outside Eternal’s first inside-host target. |
| Building a standalone agent product | LangGraph, AutoGen, CrewAI | These are application frameworks, not installable workflow packs. Use them only if Eternal’s product boundary changes. |

## What Eternal should adopt, adapt, and avoid

The checked-in Eternal design being reviewed has concrete gaps: a task router and executor do not resolve to one scope/risk decision; a low-tier quick path can be told both to omit and to create task-packet artifacts; its completion validator can require planning metadata that the low-tier plan says not to create; install profiles lack the middle ground of “maintained capability catalog available, activation selective”; the current completion record can accept a passed status without capturing the actual process exit; bounded local reviewer/concurrency limits do not cap aggregate work; and shared prose overstates Claude/Codex execution parity. These gaps explain why simply restoring the large prior package or reducing to generic instructions misses the product need.

| Decision | Mechanism and source | Current Eternal gap it addresses | Guard against overreach |
|---|---|---|---|
| **Adopt** task lanes with one decision contract | GSD/BMAD/Compound size-sensitive routing | Separate tier and scope instructions conflict; router chains and gates are not keyed to one resolved workflow | Direct tasks get no plan or agent ceremony; risk can independently raise review. |
| **Adopt** catalog availability separate from task activation | Agent Skills progressive disclosure, OpenSpec profiles, Pi skill loading | Installation offers no maintained-capability middle ground between bare core and legacy full workflow package | Available does not mean loaded or used. Keep full bodies lazy and triggers distinct. |
| **Adapt** per-host capability manifests | AIOX/ECC host sync and validation; Claude/Codex native mechanisms | Current skills and hooks do not have equal execution/enforcement on both hosts | Label enforcement honestly; test each host separately; host-native sandbox/approvals remain authoritative. |
| **Adopt** evidence-bearing, freshness-aware review | gstack fingerprints; Superpowers review roles; Compound finding synthesis | Reviewer and task ledger evidence can be stale or self-reported without proving the current diff/check | Treat agent review as analysis, not deterministic test success. Re-review after changed source. |
| **Adopt** full-run finite budgets and stop behavior | Superpowers loop cap; AutoGen/CrewAI turn/iteration controls; Ruflo cost controls | Current limits cap local loops/concurrency, not all tasks, agents, reviews, retries or time | Internal reallocation within an authorized total is fine; ask only on material scope/cost change; explicit cap is absolute. |
| **Adapt** durable state only for larger work | Spec Kit/GSD workflow state; LangGraph checkpoint model | Recovery currently depends on overlapping ledgers, host transcripts and gate assumptions | Direct/structured work uses proportionate state; resume revalidates actual repository and side effects. |
| **Adopt** capability-oriented tools with one owner | Context7, Serena, browser tools, Beads | Broad installed utilities risk overlap and unclear provenance/activation | Add only where task evidence shows value; preserve native host tools and failure diagnostics. |
| **Avoid** mandatory swarms, full story/spec lifecycle and automatic shipping | Gas Town/AIOX/gstack examples show coordination and external-effect overhead | Old orchestration stack can impose enterprise process on personal fixes | Offer those as selected capabilities only when task scope/authority warrants them. |
| **Avoid** claiming success from prompt artifacts or vendor benchmarks | SWE-agent trajectories; AGENTS studies; candidate docs | Existing receipt semantics can record assertions without captured execution | Evaluation must use controlled cross-host scenarios and actual command/browser evidence. |

## Validation agenda

Source review narrows the design; it does not prove the companion works. Compare native host behavior with Eternal-enabled Claude Code and Codex on the same fixtures. Keep host results separate. Capture task success against acceptance criteria, files changed, required-check evidence, unrequested scope, user corrections/interruption, tool and agent calls, retries, elapsed time, and model/tool cost. Do not combine these into an opaque single score.

At minimum, test: a one-line doc fix; known-cause regression bug; ambiguous greenfield request; small multi-file feature; high-risk auth/payment/migration change; broad cross-module change; stale reviewer output after a new edit; interruption followed by resume; worker or host-adapter failure; explicit budget exhaustion; host handoff; and a task where users have authorized preparation but explicitly prohibited publish/send/deploy. The quick path should stay quick, larger paths should preserve the entire agreed scope, resumption should not repeat side effects, and the stop condition should report incomplete work without false assurance.

Known unknowns include real task success and costs; skill-routing false positives/negatives; install and discovery friction; recovery reliability; interaction quality for novice and enterprise users; support on each current host version; tool security and dependency supply-chain risk; and licensing/redistribution of every bundled upstream capability. Repo stars, vendor claims, benchmark results from other environments, and generated file presence do not settle these questions. Verify current support and license provenance before selecting or bundling any external module.
