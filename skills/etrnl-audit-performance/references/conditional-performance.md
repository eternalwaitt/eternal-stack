# Conditional performance expertise

Run `performance-audit.mjs experts <contract.json>` after reconciling stack signals. Read every resource in the returned plan, apply it to the assigned checks and record a load receipt with resource hashes, version review, application notes and retained investigation evidence. A filename or a claim that a skill was invoked is insufficient. Resolve skills by returned path: the `orpc-patterns` bundle intentionally exposes the `orpc-fullstack` entrypoint name. Do not rename or skip it because the folder and frontmatter differ.

Use `scripts/lib/performance-expertise.mjs` as the activation registry. Detected positive signals cannot be disabled without correcting the inventory and rerunning discovery. An absent source pattern means unknown until source/runtime reconciliation establishes absence. Every unknown feature remains visible; never use an empty detection list as a clean result.

Do not preload every specialist on every audit. Load detected capabilities and expand the plan when investigation reveals new surfaces. SQL is separate from Prisma: MongoDB-only Prisma targets require Prisma expertise but do not imply SQL. Unknown Prisma datasource ownership must remain unresolved until inspected. Source detection is a seed: add runtime-discovered capabilities with retained evidence. Resolve explicit runtime declarations against deployment configuration before final classification.

## Version and instruction conflicts

Audit scope and read-only mode take precedence over a specialist's implementation, migration, installation or architecture instructions. Specialist examples identify hypotheses, not automatic fixes. Do not add layers, move data, change auth, disable validation or install packages merely because a companion demonstrates them. Load relevant sections of large companions progressively, but account for every performance section before closing their receipt.

- The bundled oRPC entrypoint documents a 1.x baseline; the public current documentation also exposes a newer major and a versioned v1 site. Resolve installed package/lockfile versions and use matching primary documentation before prescribing APIs. Do not apply newer-major plugin names to an older target. Compare request batching with the target's HTTP protocol and stream behavior; batching is not a universal improvement.
- Prisma `include` does not inherently prove a single SQL join or bounded child materialization. Inspect the selected relation loading strategy, database/version and emitted query count. Bound root and child collections separately. Pool options and defaults depend on Prisma's engine/driver adapter; do not transplant legacy URL options into a different engine. A cached client declaration is not proof of a singleton shared across deployed isolates.
- A sequential scan does not prove an index is missing, and an index-only scan is not universally best. Do not create duplicate indexes on already-indexed unique fields or prescribe indexes solely from schema syntax. Compare the actual plan and write/storage tradeoffs. `EXPLAIN ANALYZE` executes statements; use an authorized representative target.
- TanStack/oRPC retry layers can multiply attempts; capture total upstream calls before adding retry. Deduplication and cache keys must retain viewer/tenant/permission semantics. Preserve validation and cancellation while measuring overhead.
- Resilience examples are options for a measured bottleneck. A new queue, cache, circuit breaker or repository layer requires causal evidence and correctness verification; source patterns alone do not justify architectural changes.

Primary anchors: [oRPC v1 documentation](https://v1.orpc.dev/docs), [current oRPC batching](https://orpc.dev/docs/plugins/batch), [Prisma relation loading](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries), [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html), [TanStack Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults). Resolve the target's versions; current URLs alone do not establish compatibility.

## Full investigation and rerun discipline

Do not stop after the first finding, five findings, high-severity findings or one example per pattern. Priority orders work and the executive summary; it never removes a discovered operation from investigation. Keep the complete structured findings ledger in the common artifact even when the human summary shows only five items.

The contract requires an initial producer-tracing pass and a coverage-challenge pass. Both cover every check/surface cell and its journeys, including surfaces where earlier findings already exist. The second pass revisits clean conclusions, searches sibling implementations, checks raw/non-ORM paths, follows remaining dependencies and challenges fixture scale, limits, auth states and timing assumptions. Do not simply copy the first pass's conclusions. Retain the distinct analysis and evidence. If another issue appears, perform another complete coverage challenge before claiming completion. There is no finding-count cap. A genuine tool, fixture or runtime blocker permits an explicitly source-limited report; it never becomes a clean result or an unmentioned lower-priority omission.

Search prior run artifacts before calling this a first run. On reruns, retain the previous contract with a hash and reconcile every old/new fingerprint using `performance-audit.mjs reconcile <previous.json> <current.json>`. Stable fingerprints use check id, source file/symbol location and causal mechanism; avoid line-number-only identity. Carried issues retain identity. Disappearing findings need verification or evidence that the surface was removed. Newly reported issues require classification as previously missed, introduced by remediation, or newly observable, with causal evidence. Changed source alone does not prove introduction; new observability requires an exact new signal. Misses require an explanation of the failed investigation and a safeguard.

The helper computes a failed audit-quality label when the missed batch is at least the size of the previous finding batch (minimum one). Smaller missed batches remain `misses_detected`; do not hide either behind a clean label. This diagnoses the prior audit's recall, not whether the newly reported bottleneck is real. No validator can prove exhaustive semantic discovery or truthful telemetry; the two-pass evidence and reconciliation rules make omissions reviewable instead of silently resetting the audit each run.
## Receipt shape and review procedure

Use `tests/fixtures/performance/fixture.mjs` to inspect the complete schema, never as real measurement evidence. A loaded expertise row contains `id`, all assigned `checkIds`, `status: loaded`, `resources` with logical path and current hash, `versionReview`, `application` and retained `artifacts`. A blocked row contains the same check coverage and an exact dependency/action; completion stays source-limited.

Each `rounds` entry contains its sequential number, current inventory hash, investigation approach and all rows returned by `cells`. Each examined row retains journey ids, executed commands, raw artifacts, distinct analysis and all discovered finding ids. Findings contain check id, stable source/symbol location, causal mechanism, impact and evidence; compute their id with `findingFingerprint`. Mirror every finding in the common audit report. Add newly discovered operations to inventory/surfaces, recompute the cell matrix and investigate the expanded matrix in full before closure.

For `rerun.mode: comparison`, retain the previous contract as a hash-bound artifact and resolve every generated reconciliation row. For `first_run`, retain the actual history search. Never relabel an existing target as new to discard audit history. The target id must identify the same application across worktrees and directory renames; replace the discovery basename seed with a stable project identity.
